# From Backup to Recovery: Designing a Disaster-Recovery Strategy for a Bare-Metal Linux Server

Backup, backup, backup. How often have we heard that warning? And for good reason. Lose the only copy of all those important files and, unless you're very very lucky, they're gone for good.

But backing up a production server is a different problem. The data is only part of what makes up a working system. There is also the operating system, installed packages, services and daemons, web-server configuration, security settings, scheduled jobs, application dependencies, database engines and all the small configuration changes accumulated over years of running the machine. Different applications may even require different versions of the same software. PHP is a common example. Containerization can help by allowing individual applications to carry their own runtime environments rather than forcing every dependency onto the host operating system. But those environments can also change as applications are developed and maintained, so simply reinstalling the original container image may not reproduce the system as it actually existed before the failure.

Anyone who has had to reinstall a desktop operating system knows that getting everything back exactly as it was takes considerably longer and requires more effort than just installing the OS itself. With a server, restoring the files but not the environment leaves you with all the data and no working service. A useful disaster-recovery plan therefore has to answer a more difficult question: **how do you rebuild the entire system?**

There is also the question of time. Being able to reconstruct a server eventually is not the same as being able to restore it quickly enough to be useful. Reinstalling packages, pulling application source from repositories, recreating runtime environments and reconstructing configuration may all be possible, but every manual step extends the outage. In a real recovery situation, the objective is not only to preserve what is needed to rebuild the system, but to get it back into service as quickly as possible.

The simplest answer would be to keep a complete off-server copy of everything. In this case, however, that would require enough remote storage to accommodate a bare-metal Linux server with multiple RAID-backed disks, a huge `/var/lib` directory containing hundreds of gigabytes of database data, Docker containers and their persistent data, and the rest of the operating system and application environment. A sufficiently large remote backup allocation would make the problem much easier, but the cost of that additional storage can add up quickly.

For our case study, which is based on a real production server, we have 500 GB of remote backup space available, but that is not enough and so, will be expanding that to 1 TB. While it keeps the recurring cost reasonable, it still leaves us with a fundamental constraint: the backup destination is smaller than the total amount of data we need to protect.

The answer is not simply to leave important data out. Different parts of a server have different recovery requirements and do not all need to be protected in the same way. The operating system and its configuration can be handled differently from a multi-hundred-gigabyte database; database data can be protected differently from Docker state; and some components can be rebuilt while others must be restored exactly. The strategy described here combines those approaches into a hybrid recovery plan intended to make the complete server recoverable without requiring enough remote space to hold a conventional full copy of every byte.
