# From Backup to Recovery: Designing a Disaster-Recovery Strategy for a Bare-Metal Linux Server

Backup, backup, backup. How often have we heard that warning? And for good reason. Lose the only copy of an important file and, unless you're very lucky, it's gone.

But backing up a production server is a different problem. The data is only part of what makes the system work. There is also the operating system, installed packages, services and daemons, web-server configuration, security settings, scheduled jobs, application dependencies, database engines and all the small configuration changes accumulated over years of running the machine. Different applications may even require different versions of the same software. PHP is a common example, and containerization adds another layer by allowing individual applications to carry their own runtime environments rather than forcing every dependency onto the host operating system.

Anyone who has reinstalled a desktop operating system knows that getting everything back exactly as it was can take considerably longer than installing the OS itself. With a server, restoring the files but not the environment that uses them may leave you with all your data and still no working service. A useful disaster-recovery plan therefore has to answer a more difficult question: **how do you rebuild the entire system?**

The simplest answer would be to keep a complete off-server copy of everything. In this case, however, that would mean protecting a bare-metal Linux server with multiple RAID-backed disks, a separate filesystem mounted under `/var/lib`, hundreds of gigabytes of MariaDB data, Docker containers and their persistent data, and the rest of the operating system and application environment. A sufficiently large remote backup allocation would make the problem much easier, but it also means allocating considerably more storage than may otherwise be necessary.

For our case study, which is based on a real production server, we have 500 GB of remote backup space available and will be expanding that to 1 TB. That keeps the recurring cost reasonable, but it still leaves us with a fundamental constraint: the backup destination is smaller than the total amount of data we need to protect.

The answer is not simply to leave important data out. Different parts of a server have different recovery requirements and do not all need to be protected in the same way. The operating system and its configuration can be handled differently from a multi-hundred-gigabyte database; database data can be protected differently from Docker state; and some components can be rebuilt while others must be restored exactly. The strategy described here combines those approaches into a hybrid recovery plan intended to make the complete server recoverable without requiring enough remote space to hold a conventional full copy of every byte.
